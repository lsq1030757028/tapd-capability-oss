# tapd-business-queries · 业务问答与状态语义层

状态：`draft`。本文只定义要做什么和怎么验，不授权实现，也不新增任何 TAPD 写操作。

上游决策（本规格的边界由它们划定，不在此重议）：

- `test-partner/docs/decisions/0003-tapd-use-official-mcp.md` — 通用 TAPD 接入改用官方 `mcp-server-tapd`，自研件定位收窄为治理层。
- `test-partner/docs/decisions/0004-tapd-line-takeover.md` — 本 spec 按 0003 边界继续写；通用原始查询与 CRUD 明确不做；验收维持"业务问题能答且答对"的可观测口径。

## 1. 这一层解决什么病

字段基线层解决的是"第 8 栏到底是什么"，它已经落库并跑通。但它止步于此：
基线知道某一栏叫「验收状态」，不知道「验关」这个词在这个项目里对应哪几个取值，
于是人问「我还有哪些缺陷没验关」时，能力面只能把原始条目倒出来让人自己数。

倒出来让人自己数，就是把出错的位置从机器挪到人身上——而这正是基线层当初要治的那个病
（错配置带病运行 98 天，因为没有任何东西会报警）。

所以本层做且只做一件事：**把工作区里的原始状态/字段取值，映射成业务能听懂的谓词，并用它直接回答业务问题**。
通用取数不在这里做，官方 `mcp-server-tapd` 已经做得更好且跟进 TAPD API 变更。

## 2. 范围

### 2.1 接通（不新增地基）

- 复用既有传输层 `src/transport_http.py` 与凭据机制（环境变量或数据目录下的凭据文件），
  不新开第二条 HTTP 通路，不新增凭据入口。
- 复用契约 C1/C2/C9：统一信封（`operation_id` / `status` / `effect` / `data` / `page` / `evidence` / `error`）、
  平台中立核心、适配器不加自己的字段。
- **只读，写 fail-closed 维持不变**：`write.*` 与已知变更操作在打到网络之前被拒。
  本层的 `*_confirm` 只写本机语义文件（与 `tapd_baseline_confirm` 同类），TAPD 侧 `effect` 恒为 `read`。
- 复用本机存储纪律（`src/store.py`）：语义映射与基线同文件、同令牌指纹、同样存在包目录之外。
  换令牌自动失效，复制目录带不走别人的口径。

### 2.2 状态语义（本层的独有价值）

把工作区的原始取值映射成业务谓词，并据此回答问题。三件事：

1. **谓词映射**：`没验关` / `已提测` / `逾期` / `指派给我` / `属于当前迭代` 这类业务说法，
   映射到 `(工作项类型, 字段, 取值集合)` 的三元组，逐工作区、逐工作项类型独立。
2. **人闸确认**：映射不由模型拍脑袋定稿。机器给候选 + 真实条目 + TAPD 链接，人对照确认后才生效——
   与基线层 review→confirm 同型，未 review 不许 confirm。
3. **失效即拒答**：映射所依赖的字段或状态发生漂移、或谓词在这个工作区压根没有对应取值时，
   拒答相关问题并说明原因，不给一个看着像对的答案。

## 3. 明确不做

| 不做 | 为什么 | 谁承担 |
|---|---|---|
| 通用原始字段查询（任意 entity + 任意字段的自由取数） | 官方件覆盖需求/缺陷/任务/迭代且跟进 API 变更，再造一遍只会多一处要维护的偏差源 | 官方 `mcp-server-tapd` |
| 需求/缺陷/任务 CRUD（创建、修改、流转、上传、删除） | 本能力自 P0 起是只读件，写路径的审批/回读/对账契约（C4–C7）从未落地，半套写比不写更危险 | 官方 `mcp-server-tapd`；本仓维持 `WRITE_NOT_IMPLEMENTED` |
| 列表转储（把某类工作项整批倒成表格/CSV 交人自己筛） | 转储就是把判断责任推回给人，本层存在的理由恰恰是不推 | 官方件取数 + 使用者自己的表格工具 |
| 跨工作区汇总 | 字段编号与状态语义都是逐工作区独立的，跨区合并等于把两套口径搅在一起 | 不承担；真有需要另立需求 |
| 报表导出、趋势、周期统计 | 与"回答一个业务问题"不是一类东西，且需要历史留存，超出只读快照能力 | 不承担 |
| 自然语言到任意 TAPD API 的通用翻译 | 那是通用接入的另一种说法，见第一行 | 官方 `mcp-server-tapd` |

底层取数能力继续保留为诊断用途，但**不进入业务问答链路，也不面向人输出**——结果含内部编号。
其中 `tapd_list` 只保留包内函数，不注册成公共 MCP 工具；公共业务取数只暴露语义查询面。

## 4. 验收标准

验收题目是具体业务问题，口径是"系统能答且答对"。**答对 = 与 TAPD 网页在同等筛选条件下的结果集逐条 id 求差集，双向差集为空**（不漏、不多）。
证据留：时间戳、项目 id、网页侧筛选条件与条目 id 列表、系统侧返回的条目 id 列表。**不采信执行者口述**。

### 4.1 必答问题清单

| ID | 业务问题 | 覆盖维度 |
|---|---|---|
| AC-BQ-01 | 我还有哪些缺陷没验关？ | 缺陷状态 + 指派 |
| AC-BQ-02 | 当前迭代还有哪些需求没提测？ | 需求状态 + 迭代归属 |
| AC-BQ-03 | 指派给我的缺陷里，哪些已经过了预计解决时间还没解决？ | 逾期 + 指派 + 缺陷状态 |
| AC-BQ-04 | 这个迭代里指派给我的需求，有哪些已经完成、哪些还没？ | 迭代归属 + 指派 + 需求状态 |
| AC-BQ-05 | 有哪些缺陷指派给我之后一直没人动过？ | 指派 + 缺陷状态 |
| AC-BQ-06 | 有哪些需求的预计完成时间已过，但状态还没到已实现？ | 需求状态 + 逾期 |

每题的答案里必须同时给出**口径回显**：把「没验关」「没提测」「逾期」在这个工作区解释成了哪几个取值。
口径不回显的正确答案不算通过——下一次工作流被改动时，没人能判断答案是否还成立。

### 4.2 拒答类验收（同等重要）

| ID | 场景 | 期望行为 |
|---|---|---|
| AC-BQ-07 | 基线缺失或令牌指纹不匹配 | 全面拒答业务问题，指向 `tapd_baseline_review`，不退化成原始转储 |
| AC-BQ-08 | 注入字段漂移（改掉映射引用的某栏名称） | 只拒答依赖该栏的问题并点名原因，其余问题照常作答——不是一漂全停，也不是漂了照答 |
| AC-BQ-09 | 注入状态语义漂移（映射引用的状态取值在工作流里已不存在） | 拒答该工作项类型的状态类问题，提示重新核对映射 |
| AC-BQ-10 | 问一个本工作区没有对应取值的谓词（例如该项目根本没有"验关"这一步） | 明说"这个项目没有对应状态，需要你告诉我它对应哪一步"，**不做近似匹配** |
| AC-BQ-11 | 结果集超过单次取数上限 | 显式声明被截断与真实总数，不给"只有 N 条"式结论 |
| AC-BQ-12 | 任何面向人的输出 | 不出现内部字段编号，一律业务名（沿用既有硬规则） |

## 5. 语义映射的数据来源与失效行为

### 5.1 供数的三个来源

| 来源 | 供什么 | 机制 |
|---|---|---|
| 工作流状态图（`workflow.get` → `/workflows/status_map`） | 该工作区状态原始值 ↔ 中文显示名 | 传输层已有路由，但基线层尚未使用；本层第一次真正用它 |
| 已确认基线的 `in_use` 字段 | 谓词落在自定义栏位上时的可用栏位集合与业务名 | `store.load()` + `context.domains[*].in_use` |
| TAPD 内置字段 | 指派人、迭代归属、时间类字段等全局固定语义 | 无需核对（基线层已判定"走内置栏位，语义全局固定"） |

硬约束，直接继承基线层：

- **观察名单（`watchlist`）里的栏位不得参与筛选**。没核过的栏位不拿来筛，映射候选也不许引用它。
  观察名单栏位后来有值了，走 `tapd_watchlist_recheck` → 重新 review → confirm，然后才准进映射。
- **人说"映射不对"不改映射**，只重新拉真实条目交人核（沿用 `tapd_field_evidence` 的举证纪律）。
  人也会记错，唯一权威是 TAPD 实测。

### 5.2 映射记录长什么样

语义映射与基线存在同一份工作区记录里，`WorkspaceContext` 版本从 `1.1` 升到 `1.2`，新增 `semantics` 段。
每条映射至少带：谓词名、工作项类型、依赖字段、取值集合、来源（状态图 / 基线栏位 / 内置）、
用于人闸的证据条目 id 与链接、确认时间、确认时的状态图快照标识。

版本升级必须是向后兼容的读：`1.1` 的旧基线文件仍可用于基线类问题，只是所有业务问答判为"未建立语义"。

### 5.3 漂移与失效（fail-closed 分级）

答任何业务问题之前先跑廉价检查，顺序与基线层一致（先比修订号，再比内容）：

| 触发 | 行为 |
|---|---|
| 基线不可用（缺失 / 外来令牌 / 不可读） | 拒答全部业务问题，说明原因与下一步 |
| 字段漂移（`context.drift_report` 判 `drifted`） | 拒答**依赖漂移栏位**的问题，点名是哪个谓词、哪一栏、当时记作什么、现在实际是什么；不依赖它的问题继续作答 |
| 状态图漂移（快照标识变化，或映射引用的取值已消失） | 拒答该工作项类型的全部状态类问题，提示重新 review 该类谓词 |
| 谓词无映射 | 拒答该问题，请人指认对应状态；不猜、不近似匹配 |
| 该工作项类型不可读（权限/传输失败） | 如实说读不到，不用其它类型的数据替代 |

拒答不是沉默。每次拒答都要给出：拒了哪个问题、因为什么、下一步做什么、以及**此刻还有哪些问题是能答的**。

## 6. 接口草案

只定输入输出形状与语义，不定实现。四个工具面，其中三个是人闸链路，与基线层 review→confirm 同型。

### 6.1 `tapd_semantic_status(workspace_id, session_context="")`

**取数前先问它**（与 `tapd_baseline_status` 同一纪律）。

- 输入：`workspace_id`，以及可选的、由 `tapd_context_resolve` 为本次确认签发的 `session_context`
- 输出：语义层是否可用；已确认的谓词清单（谓词名、工作项类型、口径一句话、确认时间）；
  当前失效的谓词及原因；**现在能答哪些问题、不能答哪些问题**；下一步动作。
- 不含：任何内部字段编号。

### 6.2 `tapd_semantic_review(workspace_id, predicate)`

- 输入：`workspace_id`、谓词名（如 `没验关`）
- 输出：候选映射核对卡——机器认为这个谓词对应哪个工作项类型的哪一栏的哪几个取值，
  连同 1–2 条真实条目（标题 + TAPD 链接 + 该栏当前值），外加"这些取值我判为不属于该谓词"的对照。
- 语义：只出候选，不落库。候选来源必须逐条标注（状态图 / 基线栏位 / 内置字段）。
  候选为空时如实说"这个项目里找不到对应取值"，不编。

### 6.3 `tapd_semantic_confirm(workspace_id, predicate)`

- 输入：`workspace_id`、谓词名
- 输出：确认结果、已存的映射摘要
- 语义：**未经 review 拒绝确认**（`_PENDING_REVIEW` 同型的会话内待确认态）。
  人闸的定义是"你对着 TAPD 看过了"，不是"你打了个是"。
  只写本机语义文件，不触碰 TAPD。

### 6.4 `tapd_business_query(workspace_id, question, limit, session_context="")`

- 输入：`workspace_id`、业务问题（自然语言或已解析的谓词组合）、结果上限，以及可选
  `session_context`。身份只可来自经当前令牌、项目、时效和访问范围校验的该声明，或在未传
  声明时回退已保存 profile；本接口不接收裸 `tapd_identity` / `business_role`。
- 输出：
  - `可答`：布尔。为假时给出原因与下一步，`条目` 必须为空——不允许"部分可信"的答案。
  - `口径`：把问题里的每个谓词解释成了什么（业务名 + 取值，不出编号）。
  - `条目`：标题 + TAPD 链接 + 与该问题相关的几栏取值。
  - `计数` 与 `是否截断`：截断时给真实总数，不给"只有 N 条"式结论。
  - `证据`：取数时间、工作区、基线确认时间、用到的映射及其确认时间、当前可见范围声明。
- 语义：只组合已确认谓词，不即席推断新谓词。缺谓词时走 6.2，不自己补。

写边界重申：以上四个面都不引入 TAPD 写操作。`WRITE_NOT_IMPLEMENTED` 的前置拒绝保持原样。

## 7. 已知约束

1. **平台门禁未拿到**。GitHub 免费账号的私有仓不支持保护分支与 ruleset（`PUT .../protection` 返回 403）。
   "必需 CI 不绿不合并"当前是**约定 + `.githooks/pre-push` 本地补偿**，可被 `--no-verify` 绕过，
   **不等价于平台强制门禁**。本 spec 的任何"CI 绿"表述都只是信号，不是完成定义。
2. **非执行者自证的 Review 拿不到**。单人账号无法审自己的 PR，需要干净上下文的独立复核者承担。
3. **状态图只覆盖需求与缺陷**。传输层 `WORKFLOW_SYSTEMS` 只有 `story` 和 `bug`；
   任务与迭代没有状态图来源，**本期不承诺任务/迭代的状态类问答**，问到就拒答并说明。
4. **TAPD 开放 API 没有自然语言检索**。筛选只能落成字段过滤 + 分页，
   结果集大时必然分页且有上限——截断必须显式，这是 AC-BQ-11 存在的原因。
5. **"逾期"依赖时间字段与"现在"**。时区口径和"当天算不算逾期"必须写进答案的口径回显，
   不能只藏在实现里。
6. **两条链路凭据分开**（决策 0004 第 3 条）：DeepTutor/test-partner 挂官方件，Claude 工作区流程用本层。
   两个令牌可见范围可能不同，跨链路结果对账不在本层职责内。
7. **语义映射逐工作区独立，不共享**。同基线纪律：搬别人的口径过来只会把人带沟里。

## 8. 风险

| ID | 风险 | 缓解 |
|---|---|---|
| R1 | 谓词歧义：不同人对"验关""提测"理解不同，答案对某人对、对另一人错 | 口径随每个答案回显；映射必须经人闸确认一次；异议走举证而非直接改 |
| R2 | 静默漂移窗口：状态图是否带修改时间**尚未核实**。若没有，只能靠内容快照哈希识别变化 | 实现前先核实 `/workflows/status_map` 返回是否含修改时间；没有就用规范化内容哈希做快照标识，并在每次问答前比对 |
| R3 | 截断误导："没验关的只有 3 条"实际有 300 条，比答错更难发现 | AC-BQ-11 强制显式截断声明；`page.has_more` 为真时禁止输出总量结论 |
| R4 | 权限差异：令牌看不到的条目让答案偏少，但答案看起来是完整的 | 每个答案附可见范围声明；验收对照必须用同一账号的网页视图 |
| R5 | 与官方件并存造成"同一问题两个答案" | 本层只做语义问答，通用取数明确指向官方件；消费方映射照决策 0004 执行 |
| R6 | 谓词库无限膨胀，退化成"预建一堆没人用的业务规则" | 谓词只在真实问题被卡住时新增（沿用增量扩展纪律）；第 4.1 节六题是本期全部承诺 |

## 9. 非目标与完成边界

非目标：写操作、跨工作区、报表导出、趋势分析、团队共享口径、第二种宿主适配器、Blackbox 集成。

本期完成只代表：第 4 节十二条验收（六题必答 + 六条拒答）在真实工作区上跑过并留了证据。

它**不**代表：门禁已满足规范完成定义（见第 7 节第 1、2 条）、语义层已推广、
任务与迭代的状态问答已覆盖，也不代表 `tool.json` 可以从 `draft / live:false / verification:pending` 起飞。
